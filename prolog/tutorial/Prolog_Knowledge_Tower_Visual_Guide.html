Prolog in pictures

A single fact becomes a tree,
a single query sweeps that tree

What has been explained so far in code and text is drawn again on the actual ACRUX-2 System–Subsystem–Component hierarchy. Bold lines are "the path this rule is actually sweeping now", and faint lines are "parts that exist but are irrelevant to this question".

§1

Facts: the hierarchy itself

The figure below is all 12 lines of consists_of/2 facts written in facts_model.pl (or cubesat.pl).

Each line is one fact. The acrux2 → adcs arrow is the statement consists_of(acrux2, adcs). itself. A characteristic of Prolog is that no translation is needed between code and picture; written as code, the figure is exactly the following. 

% System < Subsystem < Component (overview document §6.1)
consists_of(acrux2, adcs).      consists_of(acrux2, eps).
consists_of(acrux2, comms).     consists_of(acrux2, obc).
consists_of(acrux2, payload).
consists_of(adcs, magnetorquer).
consists_of(eps, battery_pack). consists_of(eps, thermal_heater).
consists_of(comms, lora_module).consists_of(comms, antenna).
consists_of(obc, atmega_mcu).   consists_of(payload, etp_panel).
§2

Queries: only part of the picture lights up

When ?- consists_of(acrux2, X). is asked, Prolog finds and traces only the lines in the whole picture that match this pattern. 

?- consists_of(acrux2, X).
X = adcs ;
X = eps ;
X = comms ;
X = obc ;
X = payload.

Only the 5 level-2 arrows match, and the component layer below is irrelevant to this query. Seeing it as a picture makes it clear that a query does not sweep the whole graph; it lights up exactly the parts that match the pattern.

§3

Rules and unification: joining two facts

A rule joins two (or more) facts through variables to create a new relation. 

% Two levels down (System → Subsystem → Component)
assembly(X, Z) :- consists_of(X, Y), consists_of(Y, Z).

% Components that share the same parent element
sibling_component(X, Y) :- consists_of(P, X), consists_of(P, Y), X \= Y.

?- assembly(acrux2, battery_pack).
true.
?- sibling_component(battery_pack, X).
X = thermal_heater.

assembly/2 becomes true by joining the two lines acrux2 → eps → battery_pack through the intermediate variable Y (= eps). sibling_component/2 discovers that battery_pack and thermal_heater share the same parent element, eps; the dashed curve in the figure below is this "sibling" relation.

§4

Recursion: the whole picture in two lines of rules

So far it has been one or two levels, but recursion sweeps the whole picture regardless of depth. 

% Base: if it is a direct constituent
contains(X, Y) :- consists_of(X, Y).
% Recursive: go one level deeper
contains(X, Y) :- consists_of(X, Z), contains(Z, Y).

?- contains(acrux2, X).
X = adcs ; X = eps ; X = comms ; X = obc ; X = payload ;
X = magnetorquer ; X = battery_pack ; X = thermal_heater ;
X = lora_module ; X = antenna ; X = atmega_mcu ; X = etp_panel.

All 12 appear: 5 subsystems and 7 components. The rule is still two lines, yet the whole picture lights up because the second clause calls itself and descends one level at a time. Even if the Part-pair level later adds one more layer, these two lines do not need to change.

§5

Negation as failure: the absence of a connection is also a picture

\+ means "confirmed that there is no path", not "proved that they are unrelated". The two cases are compared side by side. 

independent(X, Y) :-
    component(X), component(Y), X \= Y,
    \+ contains(X, Y), \+ contains(Y, X).

?- independent(antenna, battery_pack).
true.
?- independent(acrux2, antenna).
false.
This does not mean antenna and battery_pack are "unrelated" (in reality both sit under acrux2 and share the same power budget); it means that, considering this tree alone, neither contains the other. It is the same kind of caution as the pitfall noted earlier, that "COMMS and Payload show ready as an illusion because they have no requirements": Prolog answers only within the facts it currently has.
